## 1. 文档职责与事实来源

本目录负责将内部工程里程碑改写为可发布、可验收的产品版本。每个版本只承诺一个主要用户结果；只有该版本卡的硬门禁全部通过后，才能升级版本状态。

本路线用于回答四个关键问题：

1. **当前产品真实处于哪里？**
2. **下一版只解决什么？**
3. **什么证据允许晋级？**
4. **何时可以对公众作出 1.0 承诺？**

### 1.1 事实来源权威度（Source of Truth）

当状态或数据冲突时，按以下顺序确定权威来源：

1. **当前执行状态**：[控制索引](../orchestration/index.md)、当前看板与任务卡。
2. **技术约束**：[PC 桌面移植技术方案](../pc-desktop-porting-technical-plan.md)。
3. **架构决策**：[架构决策记录](../adr/)。
4. **产品发布范围与版本承诺**：本目录。

本路线不能覆盖当前执行状态，严禁将规划中的功能写成已经实现。

### 1.2 当前决策摘要

- **当前唯一活动版本**：`0.1.0 / M0` 内部 Alpha 关闭记录。
- **当前真实状态**：M0 桌面技术链和 legacy lint closure 已 verified，提交 `a80d91b` 已存在并完成控制面技术关闭；P0-1 schema 也已 technically verified，但未用户验收、未提交、未推送。
- **当前晋级守卫**：`0.1.0` 仍不是 released；P0-2 项目存储仅为 draft-ready，不能因 P0-1 schema 通过而启动版本发布或宣称完整 P0。
- **当前下一步**：评审 P0-2 项目存储 task/session 草案，按控制索引明确派工后再进入下一条受限源码切片；不提前启动 P1 互动或公开发布。
- **当前公开口径**：已有安装包属于内部验证产物，不是公开 Beta、RC 或正式发行包。

## 2. 1.0 产品定义

`GameEditor / CineFlow Studio` 1.0 是一款面向独立互动叙事、影游和分支视频创作者的 Windows 桌面创作工具。用户必须能够独立完成以下业务闭环：

- **项目管理**：在用户选择的本地目录中创建或打开项目。
- **资产导入**：导入本地视频、音频、图片和文档。
- **核心编排**：编排场景节点、分支条件、变量和时间轴内容。
- **互动预览**：在编辑器内预览互动流程并验证不同分支。
- **可靠恢复**：应用重启或异常退出后，恢复最近一次可靠保存，或给出明确的恢复入口。
- **项目导出**：导出可迁移的标准 JSON、DOCX 剧本和包含真实资产的 ZIP 项目包。
- **渲染输出**：导出单场景最小真实 MP4 预览片。

### 2.1 1.0 非目标（Out of Scope）

1.0 不承诺完整非线性剪辑、独立游戏播放器、云同步、OSS 直接发布、应用自动更新或任意第三方 JavaScript 插件支持。

### 2.2 1.0 核心用户旅程（User Journey）

以下是一条不可拆分的正式版验收旅程。单项能力通过，不能替代整条旅程通过：

> **安装核对 → 自定义建项 → 本地资产导入 → 节点编排与双路径预览 → 可靠重开 → 受控异常恢复 → 多格式导出 → 可迁移重开**

1. **安装核对**：用户从正式渠道获得安装包，核对发布主体、版本、数字签名和发布清单中的 SHA256 摘要后完成安装。
2. **自定义建项**：首次启动后，用户在选择的本地目录创建项目，并能看到实际保存位置。
3. **本地资产导入**：用户导入至少一段本地视频、一张图片、一段音频和一份文档；应用将资产真实复制到项目目录，不以远程示例 URL 或项目外绝对路径代替。
4. **节点编排与双路径预览**：用户建立场景、分支、变量与时间轴内容，并在应用内走通至少两条不同的互动路径。
5. **可靠重开**：用户保存并退出；重启后项目、资产引用和编辑状态与最后一次成功保存一致。
6. **受控异常恢复**：用户依据产品内错误信息和公开恢复文档处理一次受控失败，不依赖开发者远程代操作，且原项目保持可恢复。
7. **多格式导出**：用户分别导出标准 JSON、DOCX 剧本、含真实资产的 ZIP 项目包，以及受支持范围内的单场景 MP4。
8. **可迁移重开**：用户将整个项目目录移动到另一位置，或复制到支持矩阵内的另一台设备后重新打开，仍能预览并继续编辑。

### 2.3 公开版成功判定（Success Metrics）

1.0 的成功标准不是“成功生成安装包”，而是必须同时满足以下五项硬指标：

- **可完成**：RC 外部验证中，至少 80% 的目标用户仅依赖安装包和公开文档独立完成核心用户旅程；样本下限见 RC 版本卡。
- **不伤数据**：不存在未关闭的项目丢失、静默损坏、资产越界或失败写回问题。任一项存在即阻断发布。
- **不假成功**：安装、保存、导入、预览和导出均以真实结果为准；失败必须显式、可诊断，不能静默降级为模拟结果。
- **可支持**：官方下载入口、快速开始、备份恢复、known issues、问题反馈和版本回退入口在正式发布前可用。
- **边界清楚**：产品界面、发布页和用户文档对支持范围与非目标保持一致口径。

## 4. 版本与证据状态定义

### 4.1 版本生命周期状态

每个版本只允许使用以下五种状态。标签含义不依赖颜色，严禁用平均完成度或主观百分比代替门禁：

| 状态         | 定义                                                   |
| ------------ | ------------------------------------------------------ |
| **planned**  | 范围已定义，尚未进入正式代码实现。                     |
| **active**   | 正在实现或验收，不能对外宣称完成。                     |
| **verified** | 版本卡内的工程与产品门禁全部通过。                     |
| **released** | 指定产物已经按对应发布通道完成分发。                   |
| **blocked**  | 存在阻止版本晋级的明确问题，并已登记责任人和解除条件。 |

### 4.2 单项能力证据等级（Evidence Level）

| 证据等级            | 定义                                             |
| ------------------- | ------------------------------------------------ |
| `mock`              | 只有 UI、示例数据或模拟结果。                    |
| `dev_verified`      | 在开发环境中真实执行通过。                       |
| `packaged_verified` | 安装包或 unpacked 产物在测试环境中真实执行通过。 |
| `release_verified`  | 自动化、人工验收和发行条件全部通过。             |

> **推进前置要求**：版本从 `planned` 改为 `active` 前，对应版本卡必须补齐范围负责人、验收负责人、目标开始时间和证据落档位置。负责人可以是同一人，但实现结论与最终验收结论必须分开记录。

## 5. 跨版本硬门禁（Hard Gates）

### 5.1 基础自动化工程门禁

每次版本晋级为 `verified` 前，CI 或指定验收环境必须无错误完成以下基线命令：

```bash
# 安装 lockfile 锁定的依赖
npm ci

# 静态类型与代码质量
npm run typecheck
npm run lint
npm run format:check

# 自动化测试
npm run test

# 生产构建
npm run build
```

从 `0.5.0` 开始，还必须执行 Windows 安装包构建、安装版 smoke 和该版本新增的 Electron E2E。更早版本卡如果明确要求打包验证，同样必须执行。任何一项失败时，版本状态都不能标记为 `verified`。

### 5.2 全局通用红线

所有版本共同遵守：

- **严禁以假乱真**：不用 mock、fallback、示例 URL 或模拟日志冒充成功。
- **不执行任意脚本**：不执行用户项目携带的任意 JavaScript。
- **不泄漏路径与密钥**：不在项目模型中保存资产绝对路径或密钥。
- **防线不后退**：不降低 lint、TypeScript、CSP 或 IPC 校验规则来通过门禁。
- **残余风险透明**：已知残余风险必须写明影响、临时措施、责任人和关闭版本。
- **用户数据优先**：用户项目不得因升级、卸载、失败导出或取消任务而丢失。

### 5.3 外部用户验证门禁（UAT Gates）

自动化与内部 smoke 只能证明工程链路，不能单独作为产品可公开使用的证据：

- **`0.5.0` 门禁**：开始使用目标用户和真实素材执行封闭验证。
- **`0.6.0` 门禁**：必须验证用户自有场景的真实 MP4 输出，而不只验证固定 fixture。
- **`0.7.0` 门禁**：必须进行首次使用测试，确认新用户只依赖产品和公开文档即可完成核心流程。
- **`0.9.0-rc.*` 门禁**：必须满足版本卡规定的样本量、核心旅程完成率和观察期，才能晋升 1.0。
- **隐私红线**：外部验证不得收集未获明确同意的项目内容；记录仅保留必要的环境、步骤、结果、错误码和用户授权的诊断信息。

### 5.4 证据落档机制

每个 `verified` 或 `released` 结论必须链接一份按 [发布证据模板](release-evidence-template.md) 填写的记录。记录至少包含源码 commit、环境、执行命令、场景结果、产物 SHA256、失败项、残余风险、验收人和日期。`not_run`、`failed` 与 `blocked` 必须原样记录，空白不能解释为通过。

## 6. 晋级与防扩张规则

### 6.1 版本晋级七步法

版本状态变更必须按以下顺序执行，严禁越级：

1. **冻结范围**：冻结当前版本范围。
2. **完成实现**：完成实现和数据迁移。
3. **通过自动化**：通过全部自动化门禁。
4. **通过安装版验收**：在指定环境完成安装版人工验收。
5. **确认用户结果**：由产品验收确认版本承诺成立。
6. **更新发布证据**：更新版本卡证据、known issues 和回退方案。
7. **执行版本与分发变更**：最后才能修改 package version 或分发产物。

- **禁止反向证明**：后续版本不能用自己的实现证明前一版本已经完成。
- **禁止带病推进**：当前版本未通过时，只允许开展不依赖失败门禁的研究，不进入下一版本的正式代码实现。

### 6.2 需求防扩张红线

任何新增功能、支持平台或公开承诺进入 1.0 前，必须回答：

1. 它是否直接改善 1.0 核心用户旅程？
2. 它是否保持本路线规定的非目标边界？
3. 它是否能在当前版本周期内形成可验证的真实证据？

> **裁决规则**：任一答案为“否”，该需求进入 1.1 候选池，不扩张 1.0。

## 7. 时间与容量基线（Estimation Baseline）

在需求不扩张，且由一名熟悉 Electron/Windows 的开发人员持续投入的前提下：

| 版本范围           | 容量基线              |
| ------------------ | --------------------- |
| `0.2.0` 至 `0.5.0` | 约 10-17 个工作日     |
| `0.6.0`            | 约 4-8 个工作日       |
| `0.7.0` 至 `1.0.0` | 约 3-5 个工程工作日   |
| **剩余工程总量**   | **约 17-30 个工作日** |

`0.7.0` 至 `1.0.0` 的基线不包含稳定性修复等待和 RC 观察期。代码签名证书申请、外部发布审批和未知旧项目迁移同样不包含在工程天数内。

> **估算边界**：这是容量基线，不是发布日期承诺。每次版本达到 `verified` 后，必须根据实际吞吐、缺陷和外部验证结果重估。范围、人员或发布依赖变化时，必须同时更新估算假设，不能只修改日期。

## 8. 发布前关键待决事项（Milestone Blockers）

以下事项若未在最晚关闭版本前形成明确决策和责任人，将直接阻断晋级：

| 决策项               | 最晚关闭版本 | 未关闭时的阻断影响                                     |
| -------------------- | ------------ | ------------------------------------------------------ |
| 正式产品名与品牌主体 | `0.7.0`      | 无法统一发布主体、应用 metadata、安装器和用户文档      |
| 正式下载与撤回渠道   | `0.7.0`      | 无法演练真实发布、停止发布和版本回退                   |
| 代码签名与时间戳方案 | `0.7.0`      | 无法验证 RC 的发布主体、签名链和可信时间戳             |
| Windows 10 支持边界  | `0.7.0`      | 无法声明准确的系统要求、测试范围和支持期限             |
| 最低硬件与测试矩阵   | `0.7.0`      | 性能和兼容性结论没有明确适用范围                       |
| 支持渠道与响应边界   | `0.9.0-rc.1` | 正式用户遇到阻断问题时没有可执行的反馈和恢复入口       |
| 隐私、许可与诊断同意 | `0.9.0-rc.1` | 无法透明、合规地分发第三方内容或收集用户授权的诊断信息 |
| 旧项目兼容版本清单   | `0.5.0`      | RC 项目迁移矩阵无法冻结                                |

> **Windows 10 特别说明**：不能仅凭“能启动”推导长期支持承诺。`0.7.0` 前必须结合决策时的微软生命周期与 Electron 支持范围，明确最低受支持 edition/build、自动化和人工测试覆盖，以及“正式支持”或“best-effort 兼容”的对外口径。
