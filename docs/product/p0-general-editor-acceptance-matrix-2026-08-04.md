## 1. 结论与边界

本矩阵把“创建或打开项目 -> 导入真实素材 -> 放入时间线 -> 基础编辑 -> 预览 -> 保存并重开 -> 输出”的 P0 闭环写成可执行验收项。它不是实现报告，也不是用户验收报告。

当前控制面已记录 M0 提交 `a80d91b` 的技术关闭；P0-1 schema 切片已独立完成 focused 技术验证，P0-2 项目目录、真实素材复制、媒体 Job、FFmpeg 输出和业务 IPC 仍未派发。完整矩阵未运行应用、安装版、端到端或用户验收，因此整条 P0 仍为 `blocked`，不得写成 `release_verified` 或 `accepted`。

### 1.1 证据等级

| 等级 | 含义                                                            | 可否关闭 P0                    |
| ---- | --------------------------------------------------------------- | ------------------------------ |
| P0   | 产品定义：行为、前置条件、成功和失败语义已冻结                  | 否，只有规格                   |
| S0   | 静态源码事实：存在状态、handler 或 UI 入口                      | 否，不能证明运行结果           |
| R0   | 运行验证：固定 commit、环境、fixture hash、日志和产物检查可复现 | 可进入产品验证，但仍需用户接受 |
| U0   | 目标用户在真实任务中完成并确认结果                              | 可接受该条                     |
| F0   | fixture、远程示例、mock、fallback、截图或旧包                   | 不可作为正式成功证据           |

### 1.2 统一判定

- 单条通过必须同时满足产品定义、源码/运行证据和用户完成条件；缺任一层即为 `needs_verification`。
- 仅有 S0 的 UI 或 handler 只能记为 `source_observed`；localStorage、远程示例 URL、模拟日志和 success fallback 只能记为 F0。
- 真实文件无法读取、路径越过项目根、schema 不合法、素材丢失、媒体探测/渲染失败、用户取消、磁盘不足或输出检查失败，必须保留明确失败状态。
- 任何核心成功项没有真实 R0 和 U0，或失败/取消项无法证明“不覆盖原项目、不生成残缺正式产物、可定位恢复”，P0 保持 `blocked`。

## 3. 端到端执行卡

执行时绑定固定 commit、应用形态、操作系统、输入 fixture SHA-256、项目目录、日志/correlationId、截图或录像、输出 hash/可播放检查和失败后的目录清单。每个 ID 分别记录 P0/S0/R0/U0，不能用同一证据批量覆盖不同层。

建议顺序：创建项目 -> 导入真实素材 -> 放入时间线 -> 移动/裁剪/分割/删除 -> Inspector 修改 -> 播放/seek -> 保存关闭重开 -> 输出；然后重复缺失素材、错误输入、取消、媒体失败、保存失败和磁盘不足。失败场景未满足保留上次成功状态和清理要求，整条链保持 blocked。
