## 1. 研究目标

验证 GameEditor 的首个商业假设：

> 对 2-15 人的互动影游、互动短剧或品牌叙事制作团队，减少分支沟通、路径检查和交接返工，是否是足够明确且可付费的价值。

本轮研究不是验证用户是否喜欢界面，也不是验证 AI 是否“看起来聪明”。研究只回答四个问题：

1. 受访者是否正在制作包含分支、选择、条件或多结局的互动内容？
2. 当前流程中，分支沟通、路径验证、素材绑定或项目交接是否造成过真实返工？
3. 受访者是否愿意用真实且获授权的项目样本参与设计合作？
4. 受访者是否愿意为稳定的生产效率、项目可靠性和交付结果付费，而不是只愿意购买定制服务？

### 1.1 本轮不验证的内容

- 不验证云同步、多人实时协作、平台分发、观众收入抽成或独立播放器。
- 不验证任意 JavaScript 插件、脚本执行或开放插件市场。
- 不把现有原型、示例项目、模拟日志、fallback 解析结果或内部演示当作用户证据。
- 不收集未获授权的剧本、视频、音频、联系方式、账号、客户名称或商业机密。

## 2. ICP 定义

### 2.1 首要 ICP

满足以下画像的团队优先进入访谈：

- 团队规模约 2-15 人，至少有 2 个角色参与内容制作或交付。
- 正在制作或最近 12 个月内完成过互动影游、互动短剧、互动广告、互动 MV 或分支叙事样片。
- 内容以视频、音频、字幕、选择、变量、条件或多结局中的两项以上组成。
- 受访者能够描述一次具体项目，而不是只讨论概念兴趣。
- 当前使用表格、文档、剪辑工程、游戏引擎、定制脚本或人工沟通来维护分支结构。
- 有下一项目、版本迭代、客户交付或团队交接计划。

### 2.2 次优 ICP

可以纳入但不作为首批结论主样本：

- 影视或游戏院校中负责互动叙事课程的教师。
- 有明确互动内容项目的品牌内容团队或广告代理商。
- 有影视 IP、漫画 IP 或短剧 IP，正在寻找多结局内容生产方式的工作室。

次优 ICP 的反馈要单独标记，不能与首要 ICP 混合计算。

### 2.3 排除对象

以下对象不进入本轮核心样本：

- 只做线性视频剪辑，近期没有互动或分支项目的人。
- 只想使用 AI 自动生成成片，不愿维护场景、条件、路径和素材结构的人。
- 只需要完整 3D 游戏引擎、复杂实时渲染或专业 NLE 后期能力的团队。
- 没有可描述的真实项目，也无法说明内容交付、返工或交接过程的人。
- 无法确认其拥有或获得项目素材使用授权的人。
- 仅愿意让 GameEditor 团队代做一部作品，不愿测试软件工作流的人。

## 3. 招募筛选表

筛选阶段只记录最小必要信息，用匿名编号代替姓名和公司名，例如 `ICP-001`。原始联系方式不写入仓库。

| 筛选项     | 合格标准                                     | 记录值                                | 结果                             |
| ---------- | -------------------------------------------- | ------------------------------------- | -------------------------------- |
| 团队规模   | 2-15 人，或能说明内容协作角色                | `2-15` / `其他`                       | `include` / `review` / `exclude` |
| 近期项目   | 12 个月内有真实互动内容项目                  | 项目类型 + 阶段                       | `include` / `exclude`            |
| 分支结构   | 至少两条路径或两个结局                       | 路径数量级                            | `include` / `exclude`            |
| 制作角色   | 编剧、导演、剪辑、策划、制片或交付负责人之一 | 角色类别                              | `include` / `review`             |
| 当前工具链 | 能说出实际使用的工具和交接方式               | 工具类别，不记账号                    | `include` / `review`             |
| 返工事实   | 能描述一次具体返工及后果                     | 事件摘要                              | `include` / `exclude`            |
| 样本授权   | 可提供脱敏流程或获授权样本                   | `yes` / `later` / `no`                | 合作资格依据                     |
| 后续项目   | 90 天内有下一项目或迭代                      | `yes` / `unknown` / `no`              | 试点优先级依据                   |
| 付费权限   | 能影响预算或能引荐决策人                     | `decision` / `influencer` / `unknown` | 试点资格依据                     |
| 研究授权   | 同意记录最小化访谈结论                       | `yes` / `no`                          | `no` 则不进入正式访谈            |

### 3.1 筛选结果规则

- **核心样本：** 团队规模、真实互动项目、具体返工事实和研究授权全部满足，且至少有一个下一项目信号。
- **设计合作候选：** 核心样本基础上，愿意使用自有或获授权样本，能安排负责人和固定试用时间。
- **付费试点候选：** 设计合作候选基础上，存在明确交付期限、预算讨论或采购流程，并愿意为软件许可/交付支持单独评估。
- **待确认：** 项目存在但没有返工、预算、授权或下一项目证据。不得计入已验证样本。
- **排除：** 不满足核心项目条件、拒绝研究授权或只需要代做服务。

## 4. 访谈执行方式

### 4.1 建议时长

| 环节       |    时长 | 目的                             |
| ---------- | ------: | -------------------------------- |
| 开场与授权 |  3 分钟 | 说明研究边界和记录方式           |
| 项目背景   |  8 分钟 | 确认真实项目和角色               |
| 当前工作流 | 12 分钟 | 还原从剧本到交付的实际步骤       |
| 返工与交接 | 12 分钟 | 找到可量化的痛点和失败成本       |
| 方案反应   |  8 分钟 | 仅展示概念流程，不冒充已实现能力 |
| 试用与付费 |  7 分钟 | 判断真实行动和付费意愿           |
| 收尾确认   |  5 分钟 | 确认后续、授权和反例             |

总时长约 55 分钟。若受访者没有真实项目，立即结束筛选，不用剩余问题制造“有效反馈”。

### 4.2 开场话术

> 感谢你参与本次研究。我们正在研究一款面向互动影游和分支叙事团队的桌面生产工具，重点是把剧本、场景、选择、素材和交付检查放在同一份项目里。今天更关注你最近真实做过的项目和当前工作方式，不是请你夸奖产品，也不是测试你的想象力。我们会记录脱敏后的事实和判断，不会把你的剧本、视频、客户名称或联系方式写入产品仓库。你可以跳过任何不方便回答的问题，也可以随时停止访谈。

### 4.3 授权确认

在开始记录前逐项确认：

- [ ] 受访者知道研究目的和预计时长。
- [ ] 受访者知道可跳过问题并随时退出。
- [ ] 受访者同意记录脱敏结论和匿名编号。
- [ ] 受访者同意是否录音/录像；未同意时不得录制。
- [ ] 受访者确认不会提交未授权的剧本、媒体、客户资料或商业机密。
- [ ] 受访者明确哪些内容可以用于内部产品决策，哪些内容禁止外部展示。

**授权文本：**

> 我同意本次访谈以匿名编号记录，用于 GameEditor 的产品研究和内部决策。我不需要提供原始剧本、媒体或客户资料。未经我另行确认，研究结论不会公开指向我、我的团队或客户。我可以要求删除尚未进入汇总的个人记录，并可以在访谈中跳过问题或终止参与。

## 5. 访谈问题与证据规则

提问顺序从事实到影响，再到方案和购买。不要先介绍完整产品功能，避免受访者只对概念表示礼貌性认可。

| 编号  | 访谈问题                                                                                   | 对应商业假设                             | 必问追问                                     | 证据记录方式                                 |
| ----- | ------------------------------------------------------------------------------------------ | ---------------------------------------- | -------------------------------------------- | -------------------------------------------- |
| `Q01` | 请讲一个你最近参与的互动影游、互动短剧或分支内容项目，从剧本开始到交付经历了哪些步骤？     | 目标团队正在做完整的互动内容生产         | 项目处于什么阶段？你负责哪一步？还有谁参与？ | 记录项目类型、阶段、角色和步骤，不记项目名   |
| `Q02` | 这个项目有多少条主要路径、选择点或结局？这些结构现在保存在哪里？                           | 分支结构是持续维护的生产对象             | 谁维护？改稿后谁同步？有没有多个版本？       | 记录结构数量级、载体类型和维护责任           |
| `Q03` | 最近一次因为分支、条件、素材或字幕没有同步而返工是什么时候？                               | 分支沟通和同步产生真实成本               | 当时错在哪里？谁发现？返工花了几小时或几天？ | 记录最近事件、触发原因、受影响角色和时间级别 |
| `Q04` | 导演、编剧、客户或测试人员如何确认某条路径真的能走通？                                     | 路径验证目前缺少低成本工具               | 需要谁现场演示？有没有漏测的结局或条件？     | 记录验证方式、参与人数、失败后果和证据载体   |
| `Q05` | 素材文件、字幕、音频和分支逻辑之间如何关联？                                               | 资产绑定和交接是项目可靠性的付费价值     | 换电脑、换协作者或移动目录后发生过什么？     | 记录工具、命名规则、链接方式、丢失/错绑事件  |
| `Q06` | 剧本改动后，你们通常怎样把改动同步到流程图、剪辑工程和实现逻辑？                           | 结构化项目可以减少跨角色交接             | 哪一步最容易漏？谁负责最后确认？             | 记录同步链、手工步骤、重复录入和责任人       |
| `Q07` | 在过去一个项目中，哪类问题最晚才被发现？它对进度、预算或客户验收造成了什么影响？           | 交付前健康检查可以降低昂贵返工           | 如果提前发现，原本可以省下什么？             | 记录问题类别、发现时点、影响等级和可避免成本 |
| `Q08` | 如果有一个工具把场景图、选择条件、素材和路径预览放在同一份项目里，你最希望它先解决哪一步？ | 首个切口应优先解决最高频/最高损失步骤    | 为什么是这一步？现在怎么替代？               | 记录用户原话、优先级、替代方案和证据强度     |
| `Q09` | 哪些功能你认为即使有了也不会改变当前制作流程？                                             | 需要明确非目标，避免功能堆叠             | 是因为不需要、不信任还是已有更好工具？       | 记录拒绝理由，作为反例而非负面情绪           |
| `Q10` | 如果只提供本地项目编辑、路径预览、项目检查和真实媒体输出，你愿意用一份真实样本试用吗？     | 本地优先的首个闭环有机会进入真实项目     | 什么条件下可以？需要谁批准？什么时候有空？   | 记录行动承诺、样本授权、负责人和时间窗口     |
| `Q11` | 你们目前为类似工具、插件、外包或人工交付支付过什么类型的费用？                             | 客户存在相邻预算，不等于愿意为本产品付费 | 费用按人、项目、年费还是服务计？谁决定？     | 记录费用类别和区间；不逼问敏感精确金额       |
| `Q12` | 如果工具能减少一次分支返工并让项目可交接，你会如何判断它值得购买？                         | 付费价值应绑定结果而非功能数量           | 需要看到什么证据？试用成功后如何采购？       | 记录购买条件、决策链、试用门槛和反对理由     |
| `Q13` | 你愿意在未来 30-90 天安排一次固定范围的设计合作吗？                                        | 真实样本和固定时间是设计合作的行动信号   | 谁参与？样本是否获授权？每周能投入多久？     | 记录 `yes/no/later`、参与人、时间和授权状态  |
| `Q14` | 如果设计合作证明有效，你们会把软件许可、交付支持和定制开发分别怎样评估？                   | 软件价值必须与人工代做和定制开发分开     | 哪一项可以进入现有预算？需要什么合同或验收？ | 记录采购形式、预算来源、服务边界和下一步     |

### 5.1 追问纪律

- 优先问“上一次什么时候发生”，少问“你觉得未来会不会”。
- 追问具体步骤、角色、时间、结果和现有替代方案，不引导受访者认同产品。
- 用户说“很痛”“很需要”时，继续追问最近一次实际损失和已采取的解决方式。
- 用户说“愿意试用”时，必须追问样本、授权人、参与人、时间窗口和成功标准。
- 用户说“愿意付费”时，必须追问预算来源、采购人、报价形式和付费触发条件。

### 5.2 证据等级

| 等级 | 允许记录的内容                           | 是否可计入 T02 验收  |
| ---- | ---------------------------------------- | -------------------- |
| `E0` | 对概念的礼貌性兴趣、泛泛建议、假设性回答 | 否                   |
| `E1` | 真实项目背景，但没有具体问题或行动       | 只能作为样本背景     |
| `E2` | 具体返工/交接事件，能说明原因和影响      | 是，计入问题证据     |
| `E3` | 愿意提供授权样本、负责人和试用时间       | 是，计入设计合作候选 |
| `E4` | 明确采购条件、预算路径或正式报价请求     | 是，计入付费试点候选 |

没有项目事实的 `E0` 不能升级为用户验证；没有行动承诺的“愿意付费”不能升级为商业证据。

## 7. 问题编码规则

编码只描述可观察事实，不把情绪、推测或产品愿望当作问题。

| 代码  | 问题类别   | 典型证据                                       |
| ----- | ---------- | ---------------------------------------------- |
| `R01` | 分支同步   | 剧本改动没有同步到流程图、剪辑或实现           |
| `R02` | 路径验证   | 选择条件、结局或不可达节点在交付前未被发现     |
| `R03` | 素材绑定   | 视频、音频、字幕或字体错绑、缺失或无法重开     |
| `R04` | 角色交接   | 编剧、导演、剪辑、策划、程序或客户之间重复录入 |
| `R05` | 版本恢复   | 改稿、换电脑、移动目录或协作后无法恢复正确版本 |
| `R06` | 输出交付   | 预览、导出、格式、时长或验收环节导致返工       |
| `C01` | 已付费替代 | 已购买工具、插件、外包或人工流程               |
| `C02` | 采购条件   | 预算来源、决策人、合同、试用或验收要求         |
| `C03` | 试用行动   | 已确认的样本、负责人、时间窗口和成功标准       |
| `X01` | 反例       | 当前工具已解决、问题低频或不愿改变流程         |
| `X02` | 非目标需求 | 通用 NLE、完整 3D 游戏、平台分发或任意脚本     |

### 7.1 反例记录规则

每次访谈至少记录一个“为什么现在不需要 GameEditor”的可能原因。反例不用于说服用户，而用于判断切口是否错误。

反例必须包含：

- 受访者当前使用的替代方案；
- 替代方案解决了哪一步；
- 剩余问题是否足以造成返工或交付风险；
- GameEditor 若要进入，必须改变的条件；
- 该反例影响的是 ICP、价值主张、产品边界还是收费模型。

若同一反例在 3 个以上首要 ICP 中重复出现，PM 必须在 T02 回调中单独升级，不得用平均分掩盖。

## 8. 设计合作与付费试点评分

评分只用于排序，不替代访谈证据。每一项使用 `0-3` 分：`0` 无证据，`1` 弱证据，`2` 有具体事实，`3` 有事实和行动承诺。

### 8.1 设计合作候选评分

| 维度         |     分值 | 评分标准                                                              |
| ------------ | -------: | --------------------------------------------------------------------- |
| 真实互动项目 |      0-3 | 近期没有项目为 0；有具体项目但未进入制作 ≤2；正在制作且有分支交付为 3 |
| 分支返工事实 |      0-3 | 没有事件为 0；能讲一件具体返工为 2；能说明影响和责任链为 3            |
| 样本授权     |      0-3 | 无法授权为 0；可提供脱敏流程为 2；已有明确授权样本为 3                |
| 负责人投入   |      0-3 | 没有负责人为 0；口头感兴趣为 1；确认参与角色和时间为 3                |
| 下一项目信号 |      0-3 | 无下一项目为 0；计划不明确为 1；90 天内有明确项目为 3                 |
| **合计**     | **0-15** | `>=11` 进入设计合作候选；`8-10` 待补证据；`<8` 暂不进入               |

### 8.2 付费试点候选评分

| 维度         |     分值 | 评分标准                                                                    |
| ------------ | -------: | --------------------------------------------------------------------------- |
| 软件价值痛点 |      0-3 | 只有审美偏好为 0；有返工事件为 2；返工影响明确且反复发生为 3                |
| 交付紧迫性   |      0-3 | 无期限为 0；有项目但时间不明为 1；有固定交付窗口为 3                        |
| 预算与决策链 |      0-3 | 不知道预算和决策人 0；可引荐决策人 2；预算路径和采购人明确 3                |
| 试用可执行性 |      0-3 | 无样本/无授权为 0；样本和负责人待确认 1；样本、负责人、时间和成功标准齐全 3 |
| 付费意愿     |      0-3 | 只愿意让团队代做为 0；愿意讨论报价为 2；明确要求正式报价或合同为 3          |
| **合计**     | **0-15** | `>=12` 进入付费试点候选；`9-11` 继续验证；`<9` 不报价                       |

### 8.3 评分防误用

- 不能用“对产品很兴奋”替代真实项目、返工和行动证据。
- 不能因为受访者是熟人、投资人或合作方而加分。
- 不能把免费试用、定制开发、人工代做和软件采购混为同一种付费意愿。
- 评分表不包含姓名、公司、邮箱或客户名称；只保留匿名编号和脱敏事实。

### 10.2 失败判定

以下任一情况都不能把 T01 标记为 `verified`：

- 访谈问题只问态度，不问真实项目、最近事件和行动承诺。
- 评分可以通过“喜欢产品”直接获得，而没有项目和返工证据。
- 研究包承诺或暗示当前尚未实现的云协作、平台分发或脚本插件能力。
- 文档写入真实个人信息、剧本、媒体、客户资料或未经授权的原始记录。
- 把本研究包的存在写成已经完成了 T02 用户验证。
- 任何非 `docs/product/icp-interview-pack.md` 文件被修改。
